# 第四阶段 4.0：管理端功能与安全现状审计

审计日期：2026-08-26  
审计范围：管理路由、页面、共享组件、Supabase 客户端调用、仓库 SQL、交互与响应式运行状态  
审计性质：只读审计；未修改数据库、RLS、接口、权限、模型或业务实现

## 1. 结论摘要

现有管理端应继续保持 `Experimental`。五个管理路由均已接入客户端路由守卫，但只有 Dashboard 和灾害事件管理包含真实数据访问代码；用户管理、系统监控、模型管理均为明确的 `RESERVED` 占位页面。

最重要的问题不是 UI，而是授权边界：当前登录由浏览器使用 Supabase anon 客户端直接查询 `app_users` 的明文密码字段，角色保存于 `sessionStorage`；仓库 SQL 又为 anon 配置了 `app_users` 全表读取/插入和 `disaster_events` 全量 CRUD 策略。因而前端路由守卫只能控制界面跳转，不能保护数据。线上是否实际执行这些 SQL 无法从仓库确认，但按仓库脚本部署时会形成明确的未授权读取、角色冒充和灾害数据写入风险。

## 2. 页面与路由

| 页面 | 路由 | 当前实现 | 成熟度 |
|---|---|---|---|
| 管理控制台 Dashboard | `#/admin/dashboard` | 查询灾害记录数和注册用户数，提供模块入口 | 部分可用 / 存在风险 |
| 灾害事件管理 | `#/admin/disasters` | 复用灾害查询组件，连接 `disaster_events` CRUD | 部分可用 / 存在风险 |
| 用户管理 | `#/admin/users` | `MODULE STATUS: RESERVED` 占位 | 仅 UI |
| 系统监控 | `#/admin/system` | `MODULE STATUS: RESERVED` 占位 | 仅 UI |
| 模型管理 | `#/admin/models` | `MODULE STATUS: RESERVED` 占位 | 仅 UI |

路由定义位于 `src/router/routes.js:1-60`。`authorizeRoute()` 在未登录时转到 `auth`，普通用户访问管理路由时转到 `user/overview`（`src/router/routes.js:78-110`）。`main.js:511-548` 在页面渲染和 Hash 变化时调用该守卫；退出登录会清除 `sessionStorage` 并回到主菜单（`src/main.js:504-509`）。

该保护完全在浏览器内执行。管理员身份来自 `app_users.role`，并缓存到 `sessionStorage.crisis_user`（`src/auth.js:19-27`）。刷新时 `refreshSessionUser()` 只凭缓存中的 username 或 id 重新读取账号，不验证 Supabase Auth 身份（`src/auth.js:55-79`）。因此它不能作为数据库授权依据。

## 3. 功能与数据真实性

### 3.1 Dashboard

- 灾害记录数：真实 Supabase count 请求，来源 `disaster_events`（`src/services/adminStats.js:4-8`、`src/disasterEvents.js:294-299`）。
- 注册用户数：真实 Supabase count 请求，来源 `app_users`（`src/services/adminStats.js:7`）。
- `DATABASE`：两项 count 均无错误时显示 `CONNECTED`，否则 `UNAVAILABLE`；不是独立健康检查。
- `STORAGE STATUS`：直接复用数据库请求状态推导 `ONLINE`，没有检查 Supabase Storage（`src/pages/admin/dashboard.js:56-60,103-107`）。
- `LAST SYNC`：请求结束后写入浏览器当前时间，不是服务端同步时间（`src/pages/admin/dashboard.js:107`）。
- 所有模块入口固定显示 `READY`（`src/pages/admin/dashboard.js:23-36`），但用户、系统、模型三个页面实际为 `RESERVED`，状态不一致。
- 没有 ECharts、地图或随机业务指标；字符逐字动画的 `setInterval()` 只改变显示，不生成数据（`src/pages/admin/dashboard.js:77-93`）。
- 请求失败会显示 `UNAVAILABLE`，计数由服务层退为 `0`；这可能让“无法读取”和“真实为零”在计数上难以区分。

结论：Dashboard 的两项计数有真实调用，但“Storage 在线”“Last Sync”“模块 READY”含义不准确，尚不能视为真实系统监控面板。

### 3.2 灾害事件管理

- 真实读取 `disaster_events`，支持灾害类型、国家、严重程度和关键词筛选（`src/disasterEvents.js:183-208`）。
- 没有分页或条数上限，默认 `select('*')` 读取所有匹配记录；数据增长后存在性能和前端渲染风险。
- 没有独立详情页；表格只显示标题、类型、地点、日期、严重程度、伤亡、状态。
- 新增、编辑、删除均连接 Supabase（`src/disasterEvents.js:249-291`），并在 UI 中检查 error 后才显示成功。
- 删除有二次确认且明确提示不可撤销（`src/disasterEventsPage.js:435-461`），但删除请求未要求返回删除行或检查受影响行数；不存在的 ID 可能被显示为删除成功。
- 表单字段与仓库 `scripts/disaster_events.sql:4-21` 基本一致，但数据库脚本没有 CHECK 约束限制枚举和非负数。
- 前端只强制标题、国家、事件日期；经济损失验证非负。伤亡和受影响人数遇到非数字时被静默写为 `0`，负数也被截为 `0`（`src/disasterEvents.js:339-375`），可能把“未知/非法”变成零。
- 管理页直接复用用户查询页面，`mode='console'` 只打开写按钮；标题仍显示“灾害事件查询”，管理定位不清（`src/pages/admin/disasterManage.js`、`src/disasterEventsPage.js:167-190`）。
- 列表加载失败后弹出错误提示并把事件数组置空（`src/disasterEventsPage.js:336-354`），页面随后与“真实空数据”外观接近。
- 创建时会重新确认缓存账号仍存在，但并不验证管理员角色；更新和删除甚至不刷新账号（`src/disasterEventsPage.js:402-418`）。真正权限完全取决于数据库策略。

结论：CRUD 代码是真实实现，但在当前 anon RLS 设计下属于高风险的“部分可用”，不应在修复授权边界前对生产数据开放。

### 3.3 用户管理

`src/pages/admin/userManage.js` 只调用统一占位渲染器。没有用户列表、分页、角色变更、禁用、删除或服务端管理 API。当前账号数据来自自建 `app_users`，不是 Supabase Auth 用户管理。

结论：仅 UI。任何删除用户、禁用账号、设置角色等操作都应通过可信服务端边界实现，不能由 anon 浏览器客户端直接操作。

### 3.4 系统监控

`src/pages/admin/systemMonitor.js` 只有描述文字和 `RESERVED` 状态，没有 Supabase、预测 API、AI API或前端构建健康检查。Dashboard 的 `CONNECTED` 只代表两次 Data API count 同时成功，不能代表整个系统在线。

结论：仅 UI。下一阶段宜改名为“系统状态”，只展示能够真实请求并定义清楚的有限状态；浏览器无法可靠得知部署构建状态、服务端资源占用或第三方 API 密钥状态。

### 3.5 模型页面

`src/pages/admin/modelManage.js` 只有占位描述，没有读取冻结 manifest、模型指标、checksum 或推理 API 健康状态，也没有训练、切换、部署按钮。当前未发现覆盖冻结 RF-T2 的网页逻辑，也未暴露模型路径或 checksum。

结论：仅 UI。推荐定位为“模型信息与运行状态”，只读展示冻结模型名称、类别、15 项特征契约、权威测试指标、完整性状态和推理 API 健康状态；不提供网页训练、切换或部署。

## 5. 数据库、RLS 与安全边界

仓库可确认：

1. 前端只配置 `VITE_SUPABASE_URL` 和 `VITE_SUPABASE_ANON_KEY`（`src/supabase.js`）；未发现 service-role key 被打包到前端。
2. `api/ai-chat.js` 可在服务端读取 `SUPABASE_SERVICE_ROLE_KEY`，该变量没有 `VITE_` 前缀；这不等于客户端暴露，但应继续限制在服务端。
3. `scripts/disaster_events.sql:29-42` 对 anon 开放 `disaster_events` 的 SELECT、INSERT、UPDATE、DELETE，条件均为 `true`。
4. `scripts/verify_created_by_fkey.sql:25-34` 对 anon 开放 `app_users` 全表 SELECT 和 INSERT；`seed-app-users.sql` 明确以明文 password 列建示例账号。
5. `src/auth.js:81-98` 在浏览器中按 username 和 password 查询用户行，因此 anon 必须能读取凭据列才能工作；这会暴露所有可读密码，并且不是 Supabase Auth 会话。
6. anon INSERT `app_users` 没有数据库侧 role 限制。虽然正常注册 UI 固定写 `role: 'user'`，调用者可以绕过 UI 直接向 Data API 提交其他 role。
7. `scripts/disaster_stats_views.sql` 创建的公开 views 没有声明 `security_invoker=true`。在线上 PostgreSQL 版本和 owner 权限未知时，视图是否绕过基础表 RLS 需要单独验证。
8. 仓库没有版本化 Supabase migration 目录；现状由若干“在 SQL Editor 手工运行”的脚本描述，无法可靠确认线上 schema 与策略版本。

因此：公开只读灾害档案可由浏览器配合只读 RLS 访问；管理员灾害 CRUD、角色变更、禁用/删除账号必须经过可信身份和授权边界。当前实现不满足该条件。

无法从当前环境确认：线上实际表结构、已部署 policy、Data API grants、Postgres 版本、view owner、安全顾问结果、真实 Supabase Auth 设置。审计没有连接线上数据库，也没有打印任何密钥。

## 6. 代码复用审计

- 灾害查询与管理复用 `disasterEvents.js` 和 `disasterEventsPage.js`：类型映射、国家显示、日期/数字格式、筛选、表格、错误提示和 CRUD 集中在同一实现。这减少重复，但读写权限仅靠 `mode` 控制 UI，必须由数据库/服务端再次授权。
- 管理端与用户端共用 `breadcrumbs.js`、Hash Router、终端外壳和全局 VAULT-0，方向正确。
- Dashboard 统计另有 `services/adminStats.js`，灾害总数复用 `countDisasterEvents()`；没有重复 ECharts 配置。
- 类型和国家映射仍是前端硬编码，且与冻结推理资产的 ISO3/类别体系不是同一职责，不能为了“统一”直接合并。
- 下一阶段可以复用只读查询、格式化、加载/错误组件；管理写操作、用户管理和健康检查必须保持服务端职责独立。

## 7. UI 与运行态审计

只读浏览器检查覆盖五个管理路由以及 1440×900、1280×600、960×600：

- 各路由均能渲染，页面中均只有一个 `#ai-face`。
- 未发现 body 级纵向双滚动或页面级横向溢出。
- Dashboard 和占位页由共享 `.vault-console--subpage` 滚动。
- 灾害管理在 1280×600 使用表格内部滚动；960×600 时 `.disaster-dashboard` 与 `.disaster-table-wrap` 都成为滚动容器，滚动职责偏复杂。
- 表格外层允许滚动，表头 sticky；但表格未设置明确最小宽度，窄屏列可能过密。
- 管理 Dashboard 标题使用较大的终端标题，灾害管理标题仍沿用用户查询页面的小像素标题，层级不一致。
- 删除确认使用红色边界和不可撤销提示；列表中的 `[DELETE]` 与普通按钮视觉差异较弱。
- 空状态存在；加载失败最终渲染为空表，仅依靠短暂通知区分失败与零记录。
- 占位页面描述克制，没有额外 AI 文案；Dashboard 的 `READY` 与占位页冲突是主要可用性问题。

浏览器审计为避免访问或修改线上数据，拦截并提供了最小只读 REST 响应。因此它验证的是路由、DOM、滚动和占位状态，不证明真实 Supabase 数据可读或 CRUD 可安全执行。被主动阻断的非本地资源产生了 3 条 `net::ERR_FAILED`，不归因于页面业务回归。

## 8. 下一阶段优先级

### P0：授权与数据安全

1. 停止使用客户端明文密码查询和可篡改 sessionStorage 角色作为授权依据；明确采用 Supabase Auth 或可信服务端会话方案。
2. 收紧 `app_users`：客户端不得读取 password；禁止 anon 任意插入角色；角色授权必须来自不可由用户修改的可信来源。
3. 收紧 `disaster_events`：公开用户只读；管理员写入必须由可信管理员身份和 RLS/服务端 API 双重约束。
4. 将当前手工 SQL 整理为可审计的版本化 migration，并只读核对线上 policy/grant/view 状态后再实施。
5. 在 P0 完成前禁用或明确封存生产环境新增、编辑、删除入口，避免前端路由守卫被误认为数据保护。

### P1：核心管理功能

1. Dashboard 只保留真实且可解释的统计：灾害记录、用户数量（若授权允许）、最后成功读取时间、各服务独立健康状态；占位模块不得显示 READY。
2. 灾害管理增加服务端分页、详情、明确失败状态、受影响行确认和数据库约束；统一“未知”与 0 的语义。
3. 用户管理先实现安全的只读列表和有限角色/状态能力；高风险 Auth 操作放在服务端。
4. “模型管理”改为“模型信息与运行状态”，只读读取冻结 manifest 和权威报告，不提供训练或切换。
5. “系统监控”改为“系统状态”，只检测可验证的 Supabase、预测 API、AI API 状态，并显示最后检查时间和失败原因类别。

### P2：UI 与体验

1. 统一管理页标题层级、导航和模块状态词。
2. 简化灾害页嵌套滚动，给表格定义合理最小宽度和横向滚动职责。
3. 将加载失败与真实空数据设计成不同持久状态。
4. 强化危险操作按钮与确认结果，增加处理中/防重复提交状态。
5. 保留 CRT/VAULT-0 身份，但降低扫描线、发光和逐字动画对长表格阅读的影响。

### P3：可选增强

- 审计日志和有限操作追踪（须先有可信身份与数据库方案）。
- 管理统计导出或论文演示所需的只读摘要。
- 不建议网页训练模型、虚假实时大屏、无场景批量操作、复杂权限层级或个人中心。

## 9. 推荐最终信息架构

1. **管理概览**：真实摘要、模块状态、最近一次成功检查。
2. **灾害档案管理**：查询、分页、详情、受控新增/编辑/删除。
3. **账号与权限**：安全的用户列表和必要的有限管理动作。
4. **模型信息与运行状态**：冻结模型档案、指标、完整性、推理健康。
5. **系统状态**：数据库、预测 API、AI API 的真实可验证状态。

不保留含义过大的“模型控制”“实时监控”名称，不增加网页训练、部署或空洞的大屏功能。
