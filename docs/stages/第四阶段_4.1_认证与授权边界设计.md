# 第四阶段 4.1：认证与授权边界设计

设计日期：2026-08-26  
阶段性质：方案设计、线上只读核对与 4.2 迁移规划  
实施状态：未执行数据库 Migration，未修改 Auth 用户、RLS、GRANT 或生产数据

## 1. 阶段结论

本项目应以 **Supabase Auth + Auth Session + PostgreSQL RLS** 替代现有 `app_users.username + app_users.password` 客户端认证。浏览器路由守卫只负责界面导航；数据库授权必须独立成立。

推荐使用 Supabase Auth `app_metadata.role` 作为唯一授权角色来源，只保留 `user` 与 `admin` 两种应用角色。角色只能由可信服务端或 Supabase Dashboard 设置。用户可编辑的 `user_metadata`、自行维护的 `sessionStorage` 以及客户端请求字段均不得参与授权。

基于当前产品必须登录后进入数据服务的既有流程，灾害档案读取限定为 `authenticated`；新增、编辑和删除仅允许 `app_metadata.role = 'admin'`。普通灾害 CRUD 可以继续使用浏览器 Supabase Data API，但必须同时受精确 GRANT 与 RLS 约束。Auth 用户列表、邀请/创建账号、修改角色、禁用或删除账号、撤销会话等操作必须在可信服务端执行。

本轮只确定方案。当前线上危险策略仍然存在，安全问题尚未修复，不能开放生产管理 CRUD。

## 2. 依据与已审计事实

### 2.1 仓库实现

- `src/auth.js` 使用浏览器 anon 客户端按 username 和 password 查询 `public.app_users`，再把 id、username、role 写入 `sessionStorage`。
- `src/router/routes.js` 的管理路由保护仅在前端执行，不能约束 Data API。
- `src/disasterEvents.js` 从浏览器直接调用 `disaster_events` 的 SELECT、INSERT、UPDATE、DELETE。
- `src/supabase.js` 只初始化公开的 URL 与 anon key；前端未发现 service-role key。
- `scripts/seed-app-users.sql`、`scripts/verify_created_by_fkey.sql` 和 `scripts/disaster_events.sql` 描述了明文账号及宽泛 anon 策略。
- 仓库没有标准 Supabase migration 目录，现有 SQL 以手工执行脚本为主。

### 2.2 线上 Supabase 只读核对

已通过授权的只读连接确认目标项目为 `crisis-data-terminal`，项目引用与本地 Supabase URL 的 project ref 一致。核对仅访问系统目录、策略、约束、Advisor 和 migration 元数据；没有查询账号行、密码或个人信息，没有执行写入或 DDL。

已确认：

1. PostgreSQL 版本为 17.6；Supabase 受管 migration 列表为空。
2. `auth.users` 存在；元数据未报告现有 Auth 用户。
3. `public.app_users` 启用 RLS，包含 `id uuid`、唯一 `username`、明文 `password text`、`display_name`、`role`、`created_at`，没有 status 字段。
4. `app_users` 存在 anon INSERT `WITH CHECK (true)`，并存在两条重复 anon SELECT `USING (true)`；anon/authenticated 的表级 GRANT 过宽。
5. `public.disaster_events` 启用 RLS；`created_by` 与 `app_user_id` 均为 uuid，且都引用 `public.app_users(id)`。
6. `disaster_events` 对 anon 的 SELECT、INSERT、UPDATE、DELETE 均为全放行；authenticated 写策略使用 `auth.uid() = created_by`，但该列引用旧 `app_users`，不能可靠表达 Auth 身份所有权。
7. `tags`、`event_tags`、`operation_logs` 也存在宽泛 anon/authenticated 策略；4.2 不能只处理主表。
8. `operation_logs.operator_id` 已引用 `auth.users(id)`，可以作为 Auth UUID 外键设计的参考。
9. 七个公开统计视图没有 `security_invoker=true`。Security Advisor 将其全部标记为 Security Definer View 错误，视图可能绕过基础表 RLS。
10. `public.set_updated_at` 未使用 SECURITY DEFINER，但 search_path 可变；Security Advisor 给出警告。
11. Performance Advisor 还报告未索引外键、重复 permissive policy，以及 RLS 中直接调用 `auth.uid()` 的 initplan 性能问题。

尚未验证：线上真实账号的数量、每个旧账号与业务记录的所有权语义、当前 Auth Email Confirmation 配置、现有生产环境是否正在使用管理 CRUD。上述事项需要在 4.2 准备阶段以最小必要范围确认。

## 3. 官方文档与变更依据

- [Supabase Auth 用户与会话](https://supabase.com/docs/guides/auth/users)：Auth 用户通过 JWT 与 RLS 关联；管理用户 API 属于服务端管理能力。
- [JWT Claims Reference](https://supabase.com/docs/guides/auth/jwt-fields)：`app_metadata` 是 JWT 的应用元数据；`role` claim 的 PostgreSQL 角色仍是 `authenticated`/`anon`，应用管理员角色需要单独判断。
- [Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security)：UPDATE 必须有 SELECT policy，并分别约束 `USING` 与 `WITH CHECK`；`user_metadata` 可由用户修改，不适合作为授权依据；视图默认可能绕过 RLS，PostgreSQL 15+ 可使用 `security_invoker=true`。
- [Securing your API](https://supabase.com/docs/guides/database/hardening-data-api)：公开 key 可以在浏览器使用，但前提是最小 GRANT 与正确 RLS；service-role/secret key 只能留在服务端。
- [2025-04-21 Auth/Storage/Realtime schema 限制](https://supabase.com/changelog/34270-restricting-access-on-auth-storage-and-realtime-schemas-on-april-21-2025)：自定义表、函数和索引不得建立在受保护的 `auth` schema 中；本方案只在 `public` 或非暴露私有 schema 建立自定义对象，并通过外键引用 `auth.users`。
- [Supabase Auth 非对称签名密钥](https://supabase.com/blog/jwt-signing-keys)：当前项目后续服务端 JWT 验证应使用官方客户端的 `getUser()`/`getClaims()` 能力，不复制或依赖旧式对称 JWT secret。

`app_metadata` 变更不会立即刷新已经签发的 JWT。角色提升或降级后必须触发会话刷新；安全敏感的降级还应撤销已有会话，避免旧 token 在过期前继续携带 admin claim。

## 4. 管理员角色方案比较

| 维度 | A：受保护角色表 | B：`app_metadata.role` |
|---|---|---|
| 安全性 | 可安全实现，但角色表自身 RLS 容易出现递归；通常需要私有 SECURITY DEFINER 辅助函数 | 普通用户不能修改 app_metadata；服务端管理 API 可受控设置 |
| RLS 表达 | 需要子查询或安全辅助函数 | 可直接检查 `(select auth.jwt() -> 'app_metadata' ->> 'role') = 'admin'` |
| 实现复杂度 | 多一张授权表、策略、同步与潜在函数 | 较少对象，适合仅 user/admin 两类角色 |
| 更新生效 | 表查询可立即生效 | JWT 刷新前可能陈旧，需显式处理会话 |
| 用户管理 | 角色列表查询方便 | Auth 用户列表和角色修改必须经服务端 Admin API |
| Vanilla JS 适配 | 前端还需安全获取展示资料 | Auth Session 可直接提供 claim；数据库仍独立校验 |
| 论文解释 | 关系模型直观，但安全函数细节较多 | “可信 Auth 元数据 + JWT + RLS”边界清晰、实现简洁 |

**主方案选择 B：`app_metadata.role`。** 本项目只有普通用户和管理员，不需要复杂 RBAC。可另建 `public.profiles` 保存 username、display_name 等非授权展示信息，但 profiles 中的任何 role 副本都不得成为授权事实来源。若未来角色结构扩展到多角色、多资源权限，再单独评估受保护角色表。

## 5. 十五项明确技术决策

| # | 推荐结论 | 理由 | 风险与实施影响 |
|---|---|---|---|
| 1 | 使用 Supabase Auth | 消除客户端明文密码查询，并让 JWT/RLS共享可信身份 | 需要迁移登录、账号和路由初始化 |
| 2 | 用户界面使用用户名 + 密码，内部确定性映射为 Auth email/password | 保留既有体验，同时使用正式 Auth Provider | 映射必须集中且无碰撞；内部邮箱不向普通用户展示 |
| 3 | 保留规范化 username 作为登录映射与展示资料 | 不作为数据库授权依据 | 仅允许 3–24 位字母、数字和下划线；旧不兼容测试账号重建 |
| 4 | `app_metadata.role` 为唯一角色来源 | 两角色场景最简单，普通用户不可自改 | 角色变化有 JWT 陈旧窗口，需刷新/撤销会话 |
| 5 | 使用 supabase-js 管理的 Auth Session | `getSession` 初始化 UI，`onAuthStateChange` 响应刷新和退出 | 不再维护自定义 sessionStorage 身份；服务端不能信任客户端对象 |
| 6 | 路由守卫等待 Auth 初始化，并检查 Session + app_metadata | 改善导航体验 | 守卫仍不是安全边界，数据库 RLS 必须独立生效 |
| 7 | 灾害读取仅向 authenticated 开放 | 与当前“登录后进入数据服务”产品规则一致，最小暴露 | 若以后要公开查询，必须单独明确放开 anon SELECT |
| 8 | 普通灾害 CRUD 使用 Data API + RLS | 现有 Vanilla JS 调用可保留，少建一层服务 | 必须精确配置 GRANT/RLS并验证；不能只靠按钮隐藏 |
| 9 | Auth 用户管理只通过可信服务端 | `auth.admin` 需要 service role，浏览器不得持有 | 需后续建立有限的 Vercel serverless 管理 API 或采用 Dashboard |
| 10 | 用户列表由服务端 Auth Admin API 读取 | 浏览器不能直接查询 `auth.users` | 可在服务端与 profiles 合并后只返回必要字段 |
| 11 | 角色修改只在可信服务端执行 | 防止自我提权 | 服务端先验证调用者 JWT 及 admin claim，再使用 service role |
| 12 | 最终废弃 `app_users` 认证职责 | 避免长期双认证和凭据泄露 | 完成引用迁移后锁定/隔离，再删除密码字段，最后评估删表 |
| 13 | 不迁移或兼容旧明文密码 | 明文不能当作安全哈希，继续兼容会保留风险 | 通过邀请、重建账号或重置密码迁移；不得读取/导出密码 |
| 14 | `created_by` 显式映射到 `auth.users.id` | 保留可追溯性且不伪造创建者 | 无可靠映射的历史记录保持 NULL；分阶段新增外键再切换 |
| 15 | 不设计复杂 RBAC | 当前仅 user/admin，两级足够 | 未来确有资源级权限需求时再演进 |

首个管理员在 4.2-B 通过 Supabase Dashboard 创建内部 Auth email/password 账号，由可信管理权限写入 `app_metadata.role='admin'`，再验证登录与 RLS。内部邮箱由规范化 username 确定性生成，不发送邮件。不得用 SQL seed 写入真实密码，也不得允许客户端提交 admin 角色。

## 6. 会话、路由与服务端边界

前端启动时先恢复 Supabase Auth Session，在状态明确前不渲染受保护页面；随后用 `onAuthStateChange` 处理登录、token 刷新、退出和会话失效。普通页面只读取当前 Auth 用户的必要展示字段。退出登录调用 Supabase Auth sign-out，不再仅清除自行维护的 storage 项。

管理路由守卫检查真实 Session 和 `app_metadata.role`，未登录转登录页，非管理员转安全的用户入口。用户即使篡改 DOM、Hash、sessionStorage 或请求体，也会在数据库 RLS 或服务端 JWT 验证处被拒绝。

服务端管理 API 必须从 Authorization header 获取访问 token，并使用 Supabase 官方 Auth 方法验证用户；不能信任客户端传入 user_id/role。验证 admin 后，才可使用仅服务端环境变量中的 service-role 执行用户列表、邀请、角色变更、禁用/删除账号和会话撤销。普通前端永远不接触 service-role key。

## 7. `disaster_events` 权限矩阵

| 操作 | anon | authenticated 普通用户 | authenticated 管理员 | GRANT / RLS | 调用边界与验证 |
|---|---|---|---|---|---|
| SELECT | 拒绝 | 允许 | 允许 | 撤销 anon；authenticated 仅 GRANT SELECT，policy `USING (true)` | 可保留前端 Data API。用无 token 请求确认拒绝，普通和管理员读取成功 |
| INSERT | 拒绝 | 拒绝 | 允许 | authenticated GRANT INSERT；policy `WITH CHECK (admin claim)` | 可保留前端 Data API。普通用户直发请求必须失败且行数不变 |
| UPDATE | 拒绝 | 拒绝 | 允许 | authenticated GRANT UPDATE；需 SELECT policy、`USING (admin claim)` 与 `WITH CHECK (admin claim)` | 可保留前端 Data API。验证普通用户更新 0 行/被拒绝，并核对数据未变 |
| DELETE | 拒绝 | 拒绝 | 允许 | authenticated GRANT DELETE；policy `USING (admin claim)` | 可保留前端 Data API。删除不存在 ID 还要检查 affected rows，不把 0 行当成功 |

这里的 admin 是 `authenticated` PostgreSQL 角色中的应用角色，不是新的数据库登录角色。策略建议使用 `(select auth.jwt() -> 'app_metadata' ->> 'role') = 'admin'`，并对 token 缺失、过期、普通用户和伪造客户端字段分别测试。

`tags`、`event_tags`、`operation_logs` 也必须按实际业务重新定义最小 GRANT/RLS。公开统计视图应改为 `security_invoker=true`，只授予所需 SELECT，并验证基础表 RLS 真正生效。`set_updated_at` 应固定安全 search_path并撤销不必要的直接 EXECUTE。

## 8. 账号与历史数据迁移

### 8.1 账号

1. 只读取旧账号的 id、username、display_name、role 等非密码字段进行盘点；不读取、打印、导出或转换 password。
2. 旧测试账号按需废弃；所需演示账号使用规范化 username 对应的内部 Auth email 重新创建，不迁移旧密码。
3. 管理员角色由可信端写入 app_metadata；普通账号省略 admin claim或明确为 user。
4. 当前规模下 username/display_name 存入 Auth user_metadata 即可，不额外建立 profiles；这些字段只用于显示，不能授权。
5. 前端全部切换至 Auth 后，撤销 `app_users` 的 anon/authenticated 权限并隔离旧表。
6. 确认没有代码、外键和报告依赖后删除 password 字段；是否最终删表在数据迁移验证后决定。

不保留旧明文登录，不建立长期双认证。旧种子脚本应删除或改成不含凭据、只能用于隔离开发环境的安全引导说明。

### 8.2 `created_by`

线上存在两个指向旧账号表的字段：`created_by` 与 `app_user_id`。不能直接替换外键并假定旧 UUID 等于 Auth UUID。

推荐分阶段：

1. 新增 nullable `created_by_auth uuid references auth.users(id) on delete set null`。
2. 建立一次性、可审计的旧账号 ID → Auth UUID 映射清单，只对确认身份的账号回填。
3. 没有可靠创建者的历史记录保持 NULL；不得为了满足外键而指定虚假的“系统用户”。如论文需要说明来源，可另保留明确的 legacy import 标志或迁移审计记录。
4. 验证记录数、非空映射数、孤儿外键和展示逻辑后，应用切换使用新字段。
5. 最后移除旧外键，按确认后的命名收敛字段；`app_user_id` 若无独立业务含义则在备份后废弃。

即使 UI 暂不展示创建者，保留 nullable Auth UUID 有助于管理员操作审计；它不应成为普通用户能修改的所有权字段。

## 9. 4.2 实施顺序（本轮未执行）

### 4.2-A：准备与备份

- 确认线上 project ref、环境、维护时间和 CRUD 冻结窗口。
- 导出 schema、policy、grant、函数、触发器和必要业务数据备份；记录 Advisor 基线。
- 核对 Supabase CLI 版本与帮助。当前没有标准 migration 目录，得到确认后用官方 `supabase migration new` 建立文件，不手写时间戳。

- 创建首个 Auth 管理员和 app_metadata role；当前不创建 profiles。
- 验证 Session 恢复、刷新、退出与角色变更后的 token 更新。

### 4.2-C：数据库授权

- 先确保管理员可用，再撤销 `app_users` 和业务表的危险 anon grants/policies，避免无安全回退的锁死。
- 为 `disaster_events` 及相关 tags/event_tags/logs 设置精确 GRANT/RLS。
- 将公开视图设为 security invoker，收紧视图 grants；修复函数 search_path 与外键索引。
- 运行 Security/Performance Advisor 和直接 Data API 权限矩阵测试。

### 4.2-D：前端迁移

- `src/auth.js` 改用 Supabase Auth；路由等待 Session 初始化并读取 app_metadata。
- 删除 password 查询和自定义 sessionStorage 角色依赖。
- 灾害 Data API 调用保持，但写操作由 RLS独立授权；错误状态不得伪装成功。

### 4.2-E：历史迁移

- 邀请/重建必要账号，生成经过确认的 ID 映射。
- 新增并回填 nullable Auth 创建者字段，验证后切换引用。
- 隔离 app_users，清理密码字段和危险 seed，仅在所有引用迁移后废弃旧认证实现。

### 4.2-F：验收与回滚

- 运行 UI、Data API、RLS、会话、伪造 storage、角色提权和登出后访问测试。
- 核对表行数、外键、受影响行数、Advisor 与前端构建。
- 只有安全矩阵完整通过后恢复生产 CRUD。

建议拆分为“Auth/资料与新外键”“GRANT/RLS/视图硬化”“旧认证清理”三个范围有限的 migration；每个 migration 只包含审阅后的最终 SQL。

## 11. 回滚设计

- 迁移前保留 schema/policy/grant 与必要数据备份，记录 Auth UUID 对应表。
- 加法步骤（profiles、新 nullable 外键、新 policy）可通过反向 migration 回滚；前端 Auth 改动可独立回退代码。
- 回滚不得恢复 anon 全量写和凭据读取策略。若新前端故障，应继续封存管理 CRUD，而不是恢复危险旧认证。
- Auth 用户邀请、密码设置和外部邮件不可通过简单 schema rollback 撤销；需依靠账号清单、会话撤销和受控停用处理。
- 删除 password、旧外键或旧表属于难以直接逆转的步骤，只能在备份、映射核对和新流程验收后执行。
- 业务记录的 `created_by_auth` 回填应保留映射快照和前后非空/孤儿统计，回滚只撤销字段引用，不破坏灾害记录。
