# 第四阶段 4.4：只读系统状态与服务健康检查

## 1. 阶段目标与边界

本阶段将原 `#/admin/system` 的 RESERVED“系统监控”占位页改为只读“系统状态 / SYSTEM STATUS”页面。页面仅执行管理员按需发起的有限健康检查，不建设持续监控、日志采集或资源监控平台，也不展示无法从真实来源确认的 CPU、内存、在线人数、请求量、成功率和运行时长。

本阶段未修改数据库结构、Migration、GRANT、RLS、认证角色来源、灾害数据、预测模型、预测接口合同、AI 气泡或用户端页面。已从当前未提交工作区创建独立 Vercel Preview 并完成自动验收；未发布 Production，未修改正式域名，也未提交或推送代码。

## 2. 实施前审计

- 路由 `#/admin/system` 已存在，并受现有管理员路由守卫保护，但页面仅为 RESERVED 占位实现。
- 管理端导航、面包屑、Dashboard 和屏幕状态栏仍使用“系统监控 / SYSTEM MONITOR”及固定 `READY` 文案。
- Supabase 前端客户端使用公开客户端密钥和 Supabase Auth Session；管理员授权仍来自可信 `app_metadata.role = "admin"`。
- `/api/health` 返回 `success`、`status`、模型名称、类别顺序和用途，不返回模型 SHA-256。
- `/api/impact-options` 是预测输入选项接口，不是健康检查接口；本页不额外调用，避免重复加载与职责混用。
- `/api/ai-chat` 只有真实生成接口，不存在低成本、无生成副作用的专用健康端点。
- 前端没有可靠的 Git Commit 注入值；“页面能够显示”也不是独立服务健康事实，因此不设置前端 Ready 卡片，不伪造构建版本。

## 3. 各检查项的准确定义

### 3.1 数据库与 Data API

页面先读取当前 Supabase Auth Session，再通过该 Session 对 `disaster_events` 执行 `head: true`、`count: "exact"` 的最小只读请求。成功必须同时满足：会话存在、Data API 无错误、返回非负整数计数。

页面区分未认证、权限不足、网络失败、超时、Data API 错误和响应格式异常。失败结果不显示为 0 条；记录数保持为“—”。耗时是浏览器发起检查到收到结果的单次往返耗时，不是数据库或服务器内部处理时间。

### 3.2 预测 API 与冻结模型

页面调用真实 `GET /api/health`，要求：

- HTTP 成功且返回 JSON；
- `success === true`、`status === "ready"`；
- 模型名称为 `Random Forest T2`；
- 类别顺序严格为 `Low / Moderate / Severe`。

HTTP 200 但模型或类别合同不一致时标记为“冻结模型合同异常”，不会显示正常。健康接口不返回 SHA-256，因此页面把模型注册表中的 SHA-256 明确标为“登记 SHA-256”，不冒充实时响应字段。

### 3.3 AI 灾害问询

页面加载和“重新检查”不会自动发送普通问答请求。AI 卡片默认显示“未执行生成验证”，由管理员手动点击后才发送一条固定、短文本、无敏感信息的灾害领域请求。检查只验证 HTTP 状态、JSON 结构和非空回答，不保存或展示回答正文。

本地自动化验证使用安全 Mock 覆盖 AI 手动检查的成功状态机。Preview 验收时由系统状态页的管理员操作显式触发且仅触发一次真实生成检查；验证只记录 HTTP/结构、非空结果、状态和耗时，不记录回答正文。

## 4. 状态判定与生命周期

页面由数据库与 Data API、预测 API、AI 服务三张卡片组成。单项状态包括：`Unchecked`、`Loading`、`Ready`、`Degraded`、`Unavailable`。总览状态只由这三项真实服务结果计算：全部已检查且正常时显示“全部已检查服务正常”；存在未验证、合同异常或服务异常时显示“部分服务异常或未验证”；检查过程中显示“检查中”。

每次安全检查创建新的周期编号和 `AbortController`。新周期会取消旧请求，旧周期结果不能覆盖新结果；检查按钮在进行中禁用。数据库和预测检查并行执行，单项失败不会阻止另一项展示。页面销毁时取消仍在运行的检查，并清理页面状态。不存在无限轮询、定时后台检查或随机状态。

## 5. 页面与导航调整

- 页面、Dashboard 入口、面包屑和屏幕状态栏统一改为“系统状态 / SYSTEM STATUS”。
- Dashboard 对该模块显示中性的 `ON DEMAND`，不再固定显示 `READY`。
- 页面沿用管理端 CRT 样式，使用文字与边框共同表达状态，不只依赖颜色。
- 页面说明明确：这是按需检查，延迟为浏览器单次请求往返耗时，结果只代表最后一次检查。

## 6. 本地验证结果

- 健康检查合同测试通过：数据库成功、未认证、无权限、异常格式；预测成功、合同不一致、非 JSON、网络失败、超时；AI 成功与异常格式；总览聚合状态。
- 完整本地环境真实请求通过：Data API 返回 16,856 条灾害记录；`/api/health` 返回 Random Forest T2 和 `Low / Moderate / Severe`。
- AI 页面加载时没有自动请求；AI 手动成功分支由 Mock 验证。
- 未登录访问跳转认证页；普通用户跳转用户总览；管理员可以访问并在刷新后重新检查。
- 合同异常和网络失败 Mock 均正确显示，且不影响数据库卡片的成功结果。
- 1920×1080、1280×720、960×600、390×844 均无页面级横向溢出；页面只有一个 VAULT-0 实例。
- 认证准备、旧认证退役、18 项预测 API 合同、模型注册表和管理员模型页回归通过。
- 模型页仍为 6 个模型档案、唯一 Production RF-T2、5 个 ECharts 图表，Severe 权重图仍为 3 条 series、15 个点。
- Vite Production Build 通过；仅保留既有 ECharts 动态导入与大 Chunk 警告。
- 重复点击验证仅产生 1 次预测健康请求；离开并重新进入页面后，迟到的旧周期结果不会覆盖新周期。

## 8. 已知限制与后续验收

- AI 状态在未手动生成验证时保持“未执行生成验证”，不能由环境变量存在推断第三方服务完全正常。
- 浏览器计时包含客户端、网络、平台和服务端整体往返，不是服务端性能指标。
- 页面不保存历史状态，不提供趋势图、告警、轮询或运行时资源指标。
- 4.4 已发布 Production，但页面仍是按需、只读状态核对工具，不等同于持续监控平台。
