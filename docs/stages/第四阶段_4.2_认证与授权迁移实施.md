## 1. 范围与已确认决定

本阶段以 Supabase Auth、真实 Session 和数据库 RLS 替代旧 `app_users` 明文登录边界。只保留普通用户与管理员；管理员由不可被普通用户修改的 `app_metadata.role = 'admin'` 判断。

已确认：

- 用户界面继续使用用户名 + 密码，不展示内部邮箱。
- 底层使用 Supabase Auth email/password Provider。
- username 只用于确定性登录映射和界面展示，不用于数据库授权。
- 不使用 `user_metadata.role`、sessionStorage、URL 或请求体 role 授权。
- 旧测试账号可以废弃重建；不迁移或兼容明文密码。
- 未登录不可读灾害档案；普通用户可读；管理员可读写。
- 不建设 SMTP、邮件邀请、密码找回、复杂会话撤销、复杂 RBAC 或用户管理后台。
- 无法可靠映射的历史 `created_by` 接受 NULL。

4.2-A 不发布、不应用 Migration、不创建线上账号。因为线上表尚无 `created_by_auth` 且旧 RLS 尚未替换，本地新认证代码不能作为当前生产版本单独发布；正确切换顺序见第 11 节。

## 2. 用户名与内部 Auth 标识

唯一实现位于 `src/authIdentity.js`：

```text
原始输入
→ 去除首尾空格
→ 转换为小写
→ 校验 3–24 字符、仅 a-z / 0-9 / _
→ normalized_username@users.cytuna.cn
```

示例：` Vault_User ` 与 `vault_user` 都规范化为同一账号 `vault_user`。大小写不区分是明确规则，而不是映射碰撞。其他不同的合法规范化用户名不会映射到同一邮箱，因为 local-part 直接保留完整用户名。

现有系统此前只检查非空，理论上允许中文、连字符、空格和短用户名。新规则不兼容这些旧测试账号；项目负责人已允许废弃并重建旧测试账号，因此没有引入哈希、编码或用户名查询服务。内部邮箱不显示在 UI、错误提示、日志、测试账号文档或截图中。

## 3. 注册、登录、Session 与退出

### 注册

公开注册入口暂时保留，调用 `supabase.auth.signUp()`：

- 前端使用统一映射函数生成内部 email。
- 密码仅交给 Supabase Auth。
- `options.data` 只写 username 和 display_name，用于显示。
- 注册函数没有 role 参数，也不写 app_metadata；新账号默认按普通用户处理。
- 不查询或写入 `app_users`，不创建旧式账号记录。
- 注册错误转换为简洁中文，不向用户展示内部邮箱或原始 Auth 细节。

内部邮箱不能接收确认邮件。4.2-B 必须在 Dashboard 人工确认 Email Provider 已启用、Confirm Email 已关闭、Allow new users to sign up 与是否保留公开注册的最终决定一致。本轮没有修改这些设置。

若 Confirm Email 关闭，signUp 会返回 Session。本页面仍要求注册后回到登录标签，因此注册逻辑立即调用 Auth sign-out，并在这一短流程中抑制路由级 Auth 事件，避免注册成功时误跳转。

### 登录和会话

- `signIn()` 复用同一用户名映射函数并调用 `signInWithPassword()`。
- `initAuth()` 清除旧 `sessionStorage.crisis_user`，先注册 `onAuthStateChange`，再用 `getSession()` 恢复 Supabase Session。
- Auth 用户被转换为最小 UI 用户对象：id、username、display_name、role。
- role 只读取 `app_metadata.role`；严格等于 admin 才是管理员，其他已登录账号全部是普通用户。
- `refreshSessionUser()` 使用 Auth `getUser()`，不再查询旧账号表。
- `signOut()` 调用 Supabase Auth sign-out，并清理旧身份缓存。

应用在 Session 检查完成前不调用首次路由渲染，避免管理内容短暂闪现。路由守卫仍只改善 UI；真正授权由 Migration 中的 GRANT/RLS承担。

## 4. 路由授权

现有 Hash Router 保持不变：

- 无 Session 访问保护页面：进入登录页。
- 普通用户访问管理路由：进入 `#/user/overview`。
- `app_metadata.role = admin`：允许管理路由。
- 修改 sessionStorage 中的 id、username 或 role 对认证与路由无效。
- Auth 事件同时比较用户 UUID 与角色；相同用户角色变化后也会重新计算路由。
- 退出后重新计算当前路由，旧管理页不再保留访问状态。

## 5. 灾害 CRUD 调整

`src/disasterEvents.js` 和 `src/disasterEventsPage.js` 已完成本地适配：

- 创建时写 `created_by_auth = 当前 Auth 用户 UUID`，不再查询 `app_users`。
- 主动删除请求 payload 中的 `created_by` 和 `created_by_auth`，再由代码写入真实 Session UUID。
- 更新不再执行旧账号存在性校验；管理员资格由 RLS判断。
- 删除使用 `.delete().eq(...).select('id').maybeSingle()` 检查实际受影响行；不存在的 ID 返回明确失败。
- 表单保存和删除增加进行中锁，防止重复提交。
- CRUD 错误转换为用户可理解的中文，不展示数据库策略或内部错误。
- `mode='console'` 仍只控制界面；普通用户手工发起写请求必须由 RLS拒绝。

由于隔离 `app_users` 后浏览器不能安全统计 Auth 用户，管理 Dashboard 的旧账号数量暂时显示 `N/A`。这不是零用户，也不是请求成功的假状态。Auth 用户统计若以后需要，应由可信服务端 Admin API 提供，属于后续管理功能范围。

## 6. Migration 文件

系统未安装全局 Supabase CLI，仓库也没有标准 Migration 目录。4.2-A 使用 Supabase 官方便携 CLI `2.115.0`，先实际读取 `migration --help`，再由 CLI 创建：

1. `supabase/migrations/20260826055135_add_auth_audit_fields.sql`
2. `supabase/migrations/20260826055138_harden_data_api_access.sql`

没有手工猜测时间戳，没有 link 远端项目，没有运行 `db push`、`migration up`、`apply_migration` 或任何线上 DDL。

### Migration 1：Auth 审计字段

- 为 `public.disaster_events` 增加 nullable `created_by_auth uuid`。
- 外键引用 `auth.users(id)`，`ON DELETE SET NULL`。
- 添加外键索引和字段注释。
- 不回填历史记录，不伪造系统创建者。
- 保留旧 `created_by` 与 `app_user_id`。
- 不创建 profiles：当前 username/display_name 放在 user_metadata 已满足展示需求；它们不参与授权。

### Migration 2：Data API 安全加固

| 对象 | anon | 普通 authenticated | admin authenticated |
|---|---|---|---|
| `app_users` | 无权限 | 无权限 | 无浏览器权限 |
| `disaster_events` | 无权限 | SELECT | SELECT / INSERT / UPDATE / DELETE |
| `tags` | 无权限 | SELECT | SELECT / INSERT / UPDATE / DELETE |
| `event_tags` | 无权限 | SELECT | SELECT / INSERT / DELETE |
| `operation_logs` | 无权限 | 无权限 | SELECT / INSERT，且 operator_id 必须为 auth.uid() |
| 七个统计视图 | 无权限 | SELECT | SELECT |

关键实现：

- 删除线上只读核对发现的危险和冲突旧 policies。
- 先 `REVOKE ALL`，再对 authenticated 授予每张表实际需要的最小表级权限。
- `disaster_events` SELECT 对 authenticated 为 true；所有写 policy 额外检查 JWT `app_metadata.role = admin`。
- INSERT 同时要求 `created_by_auth = auth.uid()`。
- UPDATE 同时设置管理员 `USING` 和 `WITH CHECK`，并保留 SELECT policy。
- 七个统计视图设置 `security_invoker = true`，撤销 anon 并只向 authenticated 授予 SELECT，使底层 RLS生效。
- `set_updated_at()` 保持 SECURITY INVOKER，只固定 `search_path = pg_catalog, public` 并撤销不必要的直接 EXECUTE；不改变函数业务体。

### Migration 3：旧认证清理

本轮没有创建不可逆清理 Migration。只有在 4.2-B 完成新 Auth 登录、权限矩阵、`created_by_auth`、备份和所有引用核验后，才另行生成并审批，可能包含：

- 删除 password 字段。
- 删除旧外键和冗余账号字段。
- 封存、改名或删除 `app_users`。
- 删除危险 seed 和旧认证核验脚本。
- 删除仅为迁移核对保留的旧材料。

## 12. 回滚

- Migration 前保存 schema、policy、grant 和必要业务数据备份。
- Migration 1 可撤销新外键、索引和 nullable 字段；它没有回填历史数据。

## 13. 局限性与状态维护

- 内部伪邮箱方案适合少量毕业设计演示账号，不适合真实邮件验证、找回密码或大规模身份治理。
- 公开注册在 Confirm Email 关闭时依赖密码强度和 Supabase 基础保护；是否保留由负责人在 4.2-B 最终决定。
- app_metadata 角色在 JWT 刷新前可能陈旧；本项目不建设企业级即时撤销机制，演示角色变更后要求重新登录。
- 浏览器 Data API 的安全性完全依赖正确应用和验证 Migration；本地代码完成不等于线上风险已修复。
- 数据库侧认证、授权与 RLS 边界已完成线上验证；生产前端发布结果见第 16 节。管理端 UI 与后续管理功能仍保持 Experimental。
